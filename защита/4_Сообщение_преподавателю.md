# Сообщение преподавателю в Telegram

## Вариант 0 — простой, человеческим языком (рекомендую этот)

Здравствуйте! Отправляю финальный проект — EAEU Regulatory Assistant.

Если коротко: это чат-бот, который отвечает на вопросы по регистрации
лекарственных препаратов в ЕАЭС и на каждое своё утверждение даёт ссылку на
конкретный пункт и страницу официального документа.

Задача взялась из моей работы — я занимаюсь клиническими исследованиями. Прежде
чем планировать исследование, надо свериться с нормативкой: нужна ли
биоэквивалентность, какой брать референтный препарат, можно ли расширить границы
для Cmax. Ответы лежат в решениях Совета и Коллегии ЕЭК — это сотни PDF, и поиск
нужного пункта вручную занимает от получаса до дня.

Просто спросить ChatGPT тут нельзя: он уверенно придумывает номера решений и
пунктов, которых не существует. В регуляторике это опаснее, чем отсутствие
ответа. Поэтому я делал не «бота поверх ChatGPT», а систему, где ответ строится
только по найденным документам.

Работает так: я скачал 755 документов с портала ЕАЭС, разобрал их с сохранением
структуры (приложение → раздел → пункт → страница), нарезал на 11 тысяч
фрагментов и построил по ним поиск. Когда приходит вопрос, система сначала ищет
подходящие фрагменты, а потом уже отдаёт их языковой модели — с инструкцией
отвечать только по ним и ставить номера ссылок. Такой подход называется RAG.

Технологии: Python, интерфейс на Streamlit. Поиск гибридный — векторный
(эмбеддинги multilingual-e5-base, хранятся в Qdrant) плюс обычный поиск по
словам BM25, результаты объединяются. Формулирует ответ gpt-4o через API.
Документы и фрагменты лежат в SQLite. Тесты на pytest, сейчас 75 штук.

Модель я не обучал и намеренно: дообученная модель хранит знание в весах, и
проверить, откуда взялось утверждение, невозможно. А тут любой факт
прослеживается до пункта документа, и новый документ добавляется за минуты.

Две вещи, которыми доволен больше всего. Первая: номера источников проставляет
не модель, а код — до того, как модель вообще что-то увидит. Она может указать
только номер из готового списка, поэтому выдумать ссылку физически не может;
если попробует, валидатор её вычеркнет. Вторая: уровень уверенности тоже считает
код по понятным признакам, а не сама модель, и пользователю показывается, из
чего этот процент сложился.

Отдельно повозился со сканами: 569 документов оказались отсканированными
картинками без текста — прогнал их через распознавание (Tesseract), после этого
качество поиска заметно выросло (Recall@10 с 0,70 до 0,82).

Ограничения написал честно: метрики оценивают качество поиска, а не
регуляторную корректность; тестовые вопросы сгенерированы автоматически и
требуют проверки специалистом; для части документов не подтверждено, что это
действующая редакция — система об этом предупреждает в каждом ответе. Это
вспомогательный инструмент, решение всё равно принимает эксперт.

В папке «защита» лежит описание проекта, разбор кода, скриншоты и презентация.
Запускается командой `streamlit run app/main.py`. Готов показать вживую и
ответить на вопросы.

## Вариант 1 — подробный, с техническими деталями

Здравствуйте! Отправляю финальный проект — EAEU Regulatory Assistant.

Это RAG-система по нормативной базе ЕАЭС: отвечает на вопросы о регистрации
лекарственных препаратов только по официальным документам, каждое требование —
со ссылкой на конкретный пункт и страницу.

**Сразу важное: мы ничего не обучали.** Используются готовые модели —
`intfloat/multilingual-e5-base` для эмбеддингов (локально) и `gpt-4o` по API.
Обучение здесь противопоказано: дообученная модель хранит знание в весах, и
проверить происхождение утверждения невозможно, а нормативка меняется. Наш
проект — это конвейер вокруг моделей, ~7 000 строк кода.

**Из чего состоит проект:**

1. `ingestion/` — подготовка базы (запускается вручную, редко):
   скачивание документов с портала ЕАЭС и реестр с SHA-256 и датой обращения →
   `parser.py` (PDF/DOCX/HTML + OCR для сканов) → `structure_parser.py` (разметка
   приложение/раздел/глава/пункт по регуляркам под структуру актов ЕЭК) →
   `chunker.py` (нарезка по границам структуры, ~1600 символов) →
   `indexer.py` (Qdrant + BM25).
2. `app/rag/` — ядро ответа: `hybrid_search.py` (вектор 40 + BM25 40, слияние
   RRF), `retriever.py` (формулировки запросов, политика уровней источников),
   `citations.py` (реестр цитат), `prompts.py` (промпт + защита от инъекций),
   `pipeline.py` (оркестрация всего пути вопроса, главный файл).
3. `app/regulatory/` — предметная логика: извлечение профиля препарата,
   классификация запроса, расчёт уверенности, валидация ответа, словарь МНН.
4. `app/ui/` — интерфейс на Streamlit: чат, регуляторная оценка, база знаний.

**Два решения, на которых всё держится:**

— Номера цитат присваиваются **кодом до вызова модели**: модель получает
пронумерованные фрагменты и может указать только номер. Она не пишет ни
название документа, ни номер решения, ни дату. Несуществующие номера удаляются
валидатором, а упоминания актов в тексте сверяются с корпусом. Выдумать
источник она архитектурно не может.

— Уровень уверенности считается **кодом по 9 наблюдаемым признакам** (сколько
источников, есть ли обязательные акты ЕАЭС, доля утверждений со ссылками,
подтверждена ли редакция) и раскладывается пользователю по вкладам. У модели
уверенность не спрашивается: её самооценка не является доказательством.

**Цифры:** 755 документов, 11 058 фрагментов, ~6 млн токенов. 569 документов
были сканами без текстового слоя — распознали через OCR, после этого Recall@10
вырос с 0,70 до 0,82, Recall@5 — с 0,64 до 0,70. Тестовый набор — 50 вопросов
по 14 темам. Проходят 75 автотестов.

**Ограничения** описаны честно: метрики измеряют качество поиска, а не
регуляторную корректность; тестовый набор машинно-сгенерирован и требует
экспертной валидации; для 615 из 755 документов действующая редакция не
подтверждена автоматически, и система сообщает об этом в каждом ответе.

В папке «защита» — подробное описание проекта, разбор кода, скриншоты работы,
текст выступления и презентация. Запуск: `streamlit run app/main.py`.

Готов показать демо и ответить на вопросы.
