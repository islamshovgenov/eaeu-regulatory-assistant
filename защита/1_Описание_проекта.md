# EAEU Regulatory Assistant — описание проекта

Ассистент регуляторной поддержки: отвечает на вопросы о требованиях к
регистрации лекарственных препаратов в ЕАЭС **только** на основании
проиндексированных официальных документов, с постраничными ссылками на них.

---

## 1. Задача

Специалист по клиническим исследованиям и регуляторике постоянно отвечает на
вопросы вида «нужно ли исследование биоэквивалентности для этой формы»,
«какой референтный препарат брать», «можно ли расширить границы для Cmax».
Ответ лежит в решениях Совета и Коллегии ЕЭК и в рекомендациях Экспертного
комитета — это сотни PDF, часть из которых сканы. Поиск по ним вручную
занимает от получаса до дня.

Обычный чат-бот на общей языковой модели для этой задачи непригоден: он
уверенно выдумывает номера решений и пунктов. В регуляторике выдуманная
ссылка хуже отсутствия ответа.

**Цель проекта:** система, которая отвечает быстро, но каждое нормативное
утверждение подтверждает ссылкой на конкретный фрагмент реального документа,
а при отсутствии основания честно отказывается отвечать.

---

## 2. Что сделано

| Компонент | Содержание |
|---|---|
| Сбор корпуса | документы скачаны с официального портала ЕАЭС; ведётся реестр с датой обращения и SHA-256 каждого файла |
| Корпус | **755 документов, 11 058 фрагментов, ~6,07 млн токенов** |
| Парсинг | PDF (текстовый слой), DOCX, HTML + **OCR для 569 сканов** |
| Разметка структуры | приложение / часть / раздел / глава / пункт / подпункт, страницы |
| Индексы | Qdrant (векторный, multilingual-e5-base) + BM25 (лексический) |
| Поиск | гибридный: 40 + 40 кандидатов → RRF-слияние → реранкинг → 12 фрагментов |
| Генерация | OpenAI gpt-4o (провайдер сменный: Anthropic / OpenAI / выкл.) |
| Проверка | цитаты присваиваются кодом до вызова модели, ответ валидируется против них |
| Уверенность | вычисляется программно по 9 факторам, каждый показан пользователю |
| Интерфейс | Streamlit: чат, структурированная регуляторная оценка, обзор базы знаний |
| Тесты | **75 тестов** (pytest) |

## 2а. Обучения модели в проекте нет — и это осознанно

Используются две **готовые** модели: `intfloat/multilingual-e5-base` для
эмбеддингов (работает локально) и `gpt-4o` по API. Ни дообучения, ни обучения
с нуля не проводилось. BM25 — не нейросеть, а формула ранжирования по частоте
слов; её «индекс» — посчитанная статистика корпуса.

Почему так: дообученная модель хранит знание в весах — проверить происхождение
утверждения невозможно, а нормативная база меняется, и при каждом новом решении
пришлось бы дообучать заново. В RAG знание лежит в поисковом индексе: документ
добавляется за минуты, а каждое утверждение прослеживается до пункта источника.

Содержание проекта — конвейер вокруг моделей: разбор документов с сохранением
структуры, гибридный поиск, реестр цитат, валидация ответа, расчёт уверенности,
предметная логика по препаратам. Это около 7 000 строк кода.

Подробный разбор кода по файлам — в `5_Как_устроен_код.md`.

## 3. Как это работает: путь одного вопроса

```
вопрос пользователя
   ↓
классификация запроса (общий / по конкретному препарату / вне области)
   ↓  детерминированные правила, без LLM
извлечение профиля препарата (МНН, форма, дозировка, тип, высвобождение)
   ↓
построение нескольких формулировок поискового запроса
   ↓
гибридный поиск: вектор (40) + BM25 (40)
   ↓
RRF-слияние → реранкинг → политика по уровням источников → 12 фрагментов
   ↓
РЕЕСТР ЦИТАТ: фрагментам присваиваются номера [1]…[12] — кодом, не моделью
   ↓
LLM получает system + вопрос + пронумерованные фрагменты (как ДАННЫЕ)
   ↓
ответ в JSON: текст, тезисы с номерами ссылок, ограничения
   ↓
ВАЛИДАЦИЯ: несуществующие номера удаляются, номера актов сверяются с корпусом
   ↓
расчёт уверенности по фактам поиска
   ↓
интерфейс: ответ → уверенность → «как получен ответ» → источники с фрагментами
```

### Ключевое решение: модель не создаёт ссылки

Модель физически не может выдумать источник, потому что она **не пишет объект
цитаты** — она указывает только целое число, которое уже существует в реестре.
Всё, что не разрешается в реальный фрагмент, удаляется валидатором и
показывается пользователю как предупреждение.

Дополнительно регулярным выражением ищутся упоминания номеров актов в тексте
(«Решение № 85») и сверяются с номерами документов в корпусе — если модель
упомянула акт, которого в базе нет, это выносится в предупреждение.

## 4. Иерархия источников

| Уровень | Что это | Как используется |
|---|---|---|
| TIER_1 | Решения Совета и Коллегии ЕЭК — обязательные акты | основа нормативных утверждений |
| TIER_2 | Руководства и рекомендации Коллегии ЕЭК | основа нормативных утверждений |
| TIER_3 | Рекомендации Экспертного комитета по конкретным МНН (467 шт.) | приоритет при вопросе именно об этом МНН |
| TIER_4 | ICH / EMA / WHO | только справочно, доля в контексте ограничена 25 % |

Если вывод опирается только на TIER_4, система обязана явно сказать, что
обязательного требования ЕАЭС в базе не найдено.

---

## 5. Уверенность как проверяемое число

Уверенность **не спрашивается у модели** — самооценка модели не является
доказательством. Она считается кодом и раскладывается на факторы:

```
Найдено источников: 2                                  +0.20
Есть обязательные акты ЕАЭС (TIER 1–2): 2              +0.25
Доля утверждений со ссылками: 100%                     +0.20
Релевантность лучшего фрагмента: 1.00                  +0.10
Ни для одного источника редакция не подтверждена         —
Итог: 0.75 → HIGH
```

Штрафы: расхождения между источниками, утратившие силу документы, отсутствие
актов ЕАЭС, недостаточность исходных данных. Если ответ не сослался ни на один
фрагмент — уверенность принудительно LOW независимо от качества поиска.

## 6. Безопасность

**Защита от инъекций через документы.** Нормативные тексты полны повелительных
формулировок («необходимо представить», «запрещается»). Фрагменты передаются
модели в явных разделителях с пометкой «это ДАННЫЕ, не инструкции»; длинные
последовательности угловых скобок внутри текста нейтрализуются, чтобы документ
не мог подделать границу фрагмента.

**Границы применения.** Запросы на медицинскую консультацию («какую дозу мне
принимать») отклоняются: инструмент регуляторный, а не клинический.

**Честный отказ.** При отсутствии основания выдаётся «Достаточное нормативное
основание в доступной базе знаний не найдено» вместо правдоподобной догадки.

## 7. Структура проекта

```
eaeu_regulatory_assistant/
├── app/                        приложение
│   ├── config.py               настройки из .env
│   ├── main.py                 точка входа Streamlit
│   ├── db/                     модели данных и SQLite-репозиторий
│   ├── rag/                    ЯДРО RAG
│   │   ├── retriever.py        построение запросов, политика источников
│   │   ├── hybrid_search.py    вектор + BM25 + RRF
│   │   ├── reranker.py         переранжирование кандидатов
│   │   ├── citations.py        реестр цитат и валидация ссылок
│   │   ├── prompts.py          системный промпт и схемы ответа
│   │   ├── generator.py        абстракция LLM-провайдера
│   │   ├── indexes.py          Qdrant + BM25, токенизация запроса
│   │   ├── embeddings.py       эмбеддинги (локальные или OpenAI)
│   │   └── pipeline.py         оркестрация всего пути вопроса
│   ├── regulatory/             предметная логика
│   │   ├── intake.py           извлечение профиля препарата из текста
│   │   ├── classifier.py       классификация запроса
│   │   ├── reasoning.py        расчёт уверенности, поиск расхождений
│   │   ├── validators.py       проверка ответа против реестра цитат
│   │   ├── inn.py              словарь МНН, морфология русских названий
│   │   └── schemas.py          строгие схемы (pydantic)
│   └── ui/                     интерфейс Streamlit
├── scripts/                    обслуживание
│   ├── evaluate.py             метрики поиска и цитирования
│   ├── check_database.py       диагностика целостности базы
│   ├── corpus_stats.py         статистика корпуса
│   └── make_screenshots.py     скриншоты приложения для материалов
├── tests/                      75 тестов
├── docs/                       архитектура, источники, оценка, ограничения
├── data/, database/            корпус и индексы
└── _архив_сборки_базы/         конвейер, которым база была собрана:
                                загрузка с портала, парсинг PDF, OCR сканов,
                                разметка структуры, нарезка, индексация
```

Проект разделён надвое сознательно. В `app/` и `scripts/` — то, что исполняется
при ответе на вопрос (7 000 строк, из них 2 800 — исполняемый код, остальное
комментарии). В `_архив_сборки_базы/` — 4 500 строк конвейера, который один раз
собрал базу: скачал 755 документов, распознал 569 сканов, нарезал 11 058
фрагментов и построил индексы. При работе приложения этот код не запускается,
поэтому он вынесен из рабочего дерева, но приложен к работе целиком —
с инструкцией, как вернуть и запустить.

## 8. Результаты оценки

Набор из 50 вопросов по 14 регуляторным темам.

| Метрика | До OCR | После OCR |
|---|---|---|
| Recall@5 | 0,64 | **0,70** |
| Recall@10 | 0,70 | **0,82** |
| MRR | 0,48 | 0,467 |
| Вопросов без релевантного документа | 15 | **9** |

Распознавание 569 сканов дало +12 п.п. Recall@10 и сократило «слепые зоны»
корпуса почти вдвое. MRR слегка снизился: фрагментов стало вдвое больше, и
конкуренция за первые позиции выросла.

**Метрики измеряют поиск, а не регуляторную корректность.** Набор вопросов
сгенерирован автоматически и помечен как требующий экспертной валидации; оценка
ответов языковой моделью-судьёй сознательно не используется как критерий
качества.

## 9. Ограничения (заявлены честно)

- Действующая редакция подтверждена автоматически не для всех документов: у 615
  из 755 стоит `requires_expert_validation` — перед использованием вывод нужно
  сверить с официальным источником.
- 126 файлов на других языках Союза исключены из индекса (корпус русскоязычный).
- 15 файлов форматов `.doc` / `.rtf` не разобраны.
- Текст 569 документов получен OCR — возможны ошибки распознавания, это
  помечено в карточке документа.
- Система вспомогательная: итоговое решение принимает уполномоченный эксперт.
