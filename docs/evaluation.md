# Оценка качества

## 1. Что и зачем измеряется

Система состоит из двух принципиально разных частей, и они оцениваются
отдельно:

| Часть | Вопрос | Как измеряется |
|---|---|---|
| Поиск | Находит ли система нужный нормативный документ? | Recall@5, Recall@10, MRR |
| Генерация | Обоснован ли ответ найденным? | citation coverage, citation validity, распределение уровней источников, доля отказов |
| Регуляторная корректность | Правилен ли вывод по существу? | **только экспертная оценка** |

Третья строка — главная, и автоматизировать её нельзя. Метрики первых двух
строк показывают, что система *технически* работает как задумано, но не
подтверждают правильность регуляторного заключения.

## 2. Набор вопросов

`data/eval/questions.csv` — 50 вопросов, поля:

```
question_id; category; question; expected_documents; expected_topics;
expected_answer_notes; needs_expert_validation
```

Категории: `registration`, `bioequivalence`, `biowaiver`, `reference_product`,
`additional_strengths`, `modified_release`, `high_variability`,
`narrow_therapeutic_index`, `clinical_trials`, `nonclinical`, `biological`,
`smPC`, `quality`, `pharmacovigilance`.

**У всех вопросов `needs_expert_validation = true`.** Разметка ожидаемых
документов сделана автоматически по предметной логике и не является эталоном,
подтверждённым регуляторным экспертом. Поле `expected_answer_notes` описывает,
что *ожидается увидеть*, а не что *является правильным ответом*.

## 3. Метрики поиска

```powershell
python scripts/evaluate.py
python scripts/evaluate.py --top-k 20
```

* **Recall@k** — доля вопросов, для которых ожидаемый документ попал в top-k
  результатов. Совпадение документа определяется нестрого: по номеру акта
  (`№ 85`) либо по пересечению значимых слов заголовка (≥ 50 %), поскольку
  разметка ведётся на уровне документа, а не пункта.
* **MRR** — средняя обратная позиция первого релевантного документа.
* **Распределение уровней источников** — сколько фрагментов каждого TIER
  попадает в контекст. Позволяет увидеть, не вытесняют ли международные
  руководства обязательные акты.
* Отчёт по категориям показывает, какие темы покрыты корпусом хуже.

Результаты сохраняются в `data/processed/evaluation_results.json` вместе с
пофразовым разбором (`per_question`), что позволяет разобрать каждый промах.

## 4. Метрики ответов

```powershell
python scripts/evaluate.py --with-answers --limit 10
```

Требует настроенного LLM-провайдера и расходует токены.

* **citation_coverage** — доля утверждений типа `normative_requirement`,
  имеющих хотя бы одну ссылку. Цель — 1.0: валидатор понижает статус
  утверждений без ссылок, поэтому значение ниже 1.0 указывает на то, что модель
  систематически пытается утверждать без основания.
* **citation_validity** — доля идентификаторов цитат, которые разрешаются в
  реальный фрагмент. Должна быть 1.0 по построению; отклонение означает ошибку
  в конвейере, а не в модели.
* **abstention_rate** — доля ответов, где система честно указала на
  недостаточность оснований. Высокое значение на «сложных» вопросах —
  желательное поведение, а не дефект.
* **cited_source_tiers** — уровни фактически процитированных источников.

## 5. Демонстрационные кейсы

`data/eval/cases/cases.json` — 7 кейсов, проверяющих поведение:

| Кейс | Что проверяется |
|---|---|
| CASE-1 Ибупрофен 400 мг, генерик, IR | полные данные → оценка со ссылками |
| CASE-2 Омепразол 20 мг, DR | учёт отсроченного высвобождения |
| CASE-3 Высоковариабельный препарат | отдельный поиск по вариабельности |
| CASE-4 Несколько дозировок | раздел «дополнительные дозировки» не пуст |
| CASE-5 Биоаналог | обращение к правилам для биологических ЛП, иммуногенность |
| CASE-6 Только МНН («метформин») | уточняющие вопросы вместо вывода |
| CASE-7 Заведомо отсутствующая тема | явный отказ по отсутствию оснований |

Ожидаемое поведение описано текстом; автоматически сгенерированные
регуляторные выводы **не являются** эталоном.

## 6. Автоматические тесты как часть оценки

`pytest tests` (121 тест) проверяет инварианты, которые важнее любых метрик:

* пустой поиск → модель не вызывается, выдаётся отказ;
* утверждение без ссылки не может быть нормативным требованием;
* решение без ссылок не может иметь статус «требуется»;
* ссылки на несуществующие фрагменты удаляются из текста;
* упоминание номера акта, которого нет в корпусе, фиксируется в отчёте;
* текст инъекции остаётся внутри границ блока данных;
* один МНН недостаточен для категорического вывода;
* `chunk_id` стабилен между запусками.

## 7. Процедура экспертной валидации

Рекомендуемый порядок для полноценной оценки работы:

1. запустить `python scripts/evaluate.py` и зафиксировать метрики поиска;
2. отобрать 15–20 вопросов, покрывающих все категории;
3. получить ответы системы (`--with-answers` или через интерфейс);
4. попросить регуляторного эксперта оценить каждый ответ по трём шкалам:
   * корректность нормативной ссылки (пункт действительно об этом);
   * корректность применения нормы к препарату;
   * практическая полезность перечня вопросов эксперта;
5. заполнить поля `expected_answer_notes` подтверждёнными формулировками и
   перевести `needs_expert_validation` в `false` только для проверенных строк;
6. повторно измерить метрики уже на валидированном подмножестве.

До выполнения шага 5 любые числа в этом проекте следует читать как показатели
работоспособности конвейера, а не как оценку регуляторного качества.
